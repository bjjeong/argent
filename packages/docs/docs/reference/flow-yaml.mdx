A flow is a YAML file in `.argent/flows/<name>.yaml`. The agent records the file with the flow tools. You can also write or edit the file by hand. This page lists the file shape, the selectors, the directives and the `argent flow` command. For the concept, see [Record and replay flows](/docs/features/flows).

## File shape

```yaml
steps:
  - launch: com.example.app
  - await: { visible: { id: home-screen } }
  - await: { idle: true }
```

The file has four top-level keys:

| Key                     | Required | Description                                                                                     |
| ----------------------- | -------- | ----------------------------------------------------------------------------------------------- |
| `steps`                 | yes      | The list of steps. Argent runs the steps in order                                               |
| `executionPrerequisite` | no       | One sentence that names the start state. Only a fragment can declare it                         |
| `env`                   | no       | Default environment values for scripts. See [Environment values](#environment-values)           |
| `teardown`              | no       | A list of steps that Argent runs after `steps`, also after a failure. See [Teardown](#teardown) |

A flow has one of two shapes:

| Shape           | First step that is not `echo:` or `script:` | Start state                                         |
| --------------- | ------------------------------------------- | --------------------------------------------------- |
| End-to-end flow | `launch:`                                   | Argent starts the app from scratch                  |
| Fragment        | Any other step                              | The app is already in the state that the flow needs |

Argent skips leading `echo` and `script` steps when it classifies a flow. A flow that opens with an `echo` step and then a `launch:` step is still end-to-end. A flow that opens with a `script` step and then a `launch:` step is also end-to-end. Put the named start state of an end-to-end flow in a leading `echo` step.

A file does not store a device id. The runner selects the device. A `launch:` restarts the process but does not clear the app data, the account or the backend data.

When a step fails, Argent stops `steps` and reports the later steps as skipped. Argent then runs the [teardown list](#teardown).

## Selectors

A selector finds an element on the screen. Write a selector as an explicit map:

```yaml
{ id: save-button }
{ text: Save }
{ role: button }
{ id: settings-row, text: Notifications }
{ text: { matches: '^Order #\d+$' } }
```

| Field  | Match                                                           |
| ------ | --------------------------------------------------------------- |
| `id`   | Exact, case-insensitive. The test id or accessibility id        |
| `text` | Case-insensitive substring, or `{ matches: <regex> }`           |
| `role` | Case-insensitive substring of the element role                  |
| `any`  | Any element. Takes only `true`. Pair it with a relational scope |

All fields in a selector must match. An unqualified Android id also matches its qualified resource id. `identifier` is an alias of `id`. Use single quotes for a regex with a backslash. `any: true` is the only selector without its own `id`, `text` or `role`, so it needs a relational scope, for example `{ any: true, after: { text: Danger zone } }`.

A bare string, for example `tap: Save`, is a loose selector. It tries `id` first, then `text`. Prefer the map form.

When several elements match:

| Directive type                                                                | Chosen element                                                                                                                     |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Action (`tap`, `long-press`, `swipe`, `type`, `scroll-to`, `pinch`, `rotate`) | The most specific visible match: exact text or id, then the smallest frame, then reading order                                     |
| Condition (`await`, `assert`)                                                 | `exists` and `visible` hold when any match qualifies. `hidden` holds when no match qualifies. `text` reads the first visible match |

### Relational scopes

A selector can scope its matches by the frames of other elements:

| Key      | Meaning                                                 |
| -------- | ------------------------------------------------------- |
| `within` | The target is inside the frame of the anchor            |
| `after`  | The target follows the anchor in reading order          |
| `next`   | The target is the nearest match that follows the anchor |

```yaml
- tap: { text: Delete, within: { id: profile-card } }
- assert: { visible: { role: Button, after: { text: Danger zone } } }
- tap: { role: Switch, next: { text: Wi-Fi } }
```

`within` uses the visual frame, not the source tree. Reading order is top to bottom, left to right. Scopes nest, with at most six scope keys in one selector. The `await-ui-element` tool does not support scopes.

### Runner tree and discovery tree

The runner resolves a selector against a different tree than the `describe` tool:

| Platform        | Runner tree                                   | `describe` tree            |
| --------------- | --------------------------------------------- | -------------------------- |
| iOS simulator   | Native UIView hierarchy                       | Accessibility tree         |
| Physical iPhone | Accessibility snapshot of `describe`          | Same snapshot              |
| Android         | Full accessibility hierarchy                  | Trimmed interactable nodes |
| Chromium        | DOM nodes with an id, label, value or handler | Full DOM                   |
| Vega            | Toolkit page source                           | Same source                |

On an iOS simulator and Android, an id absent from `describe` can still resolve in a flow. On Chromium, an element absent from `describe` cannot resolve. On an iOS simulator, do not copy a `role` from `describe` into a selector: the runner derives the role from the view class, `describe` from the accessibility traits. On a physical iPhone, the runner and `describe` read one tree: copy ids and roles from `describe`.

## Directives

Each step contains one directive. A failed directive stops its list, `steps` or the teardown list. After `steps` stops, the [teardown list](#teardown) still runs.

| Directive    | Shape                                                              | Description                                                                                       |
| ------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `launch`     | `<app id>` or `{ native, ios, android, vega, chromium }`           | Terminate and start the app, then wait until the app is ready                                     |
| `tap`        | `<selector>`, `{ on: <selector>, times }` or `{ x, y }`            | Tap an element. `times: 2` double-taps. `x`, `y` are normalized coordinates                       |
| `long-press` | `<selector>` or `{ on: <selector>, duration }`                     | Press and hold. `duration` in milliseconds                                                        |
| `swipe`      | `<direction>` or `{ from, direction, to, by, momentum, duration }` | Move one finger across the screen. `direction` is the travel of the finger. See [Swipe](#swipe)   |
| `type`       | `{ into: <selector>, text, submit }`                               | Focus the element and type. Presses Enter unless `submit: false`                                  |
| `scroll-to`  | `{ target: <selector>, direction, within }`                        | Scroll until the target is visible. `direction` is `down` (default), `up`, `left` or `right`      |
| `pinch`      | `{ on: <selector>, scale }`                                        | Pinch around the element, or the screen center when `on` is absent. `scale` > 1 zooms in          |
| `rotate`     | `{ on: <selector>, by }`                                           | Two-finger rotation in degrees, clockwise positive. This is a gesture, not the device orientation |
| `await`      | `{ <condition>, timeout }` or `{ idle: true, stableFor, timeout }` | Wait for a condition. Default `timeout` 7500 ms                                                   |
| `assert`     | `{ <condition> }`                                                  | Check a condition now, with a fixed 1000 ms grace. Rejects `timeout`                              |
| `wait`       | `<milliseconds>`                                                   | Pause for a fixed time                                                                            |
| `snapshot`   | `<name>` or `{ name, maxMismatch, cropOn }`                        | Compare a screenshot with a stored baseline. See [Snapshots](#snapshots)                          |
| `run`        | `<path>`                                                           | Run another flow file inline. See [Composition](#composition)                                     |
| `script`     | `{ path, timeout, env }`                                           | Run a local `.mjs` or `.sh` file in a new process. See [Local scripts](#local-scripts)            |
| `when`       | `{ <condition> }` or `{ platform }`, with `steps:`                 | Run the nested steps only when the condition holds. See [Optional steps](#optional-steps)         |
| `echo`       | `<message>`                                                        | Print a message in the report                                                                     |
| `tool`       | `<tool name>`, with `args:` and optional `delayMs:`                | Call any Argent tool with the given arguments                                                     |

`tap`, `type` and `long-press` do not scroll. Add `scroll-to` before them when the target can be off-screen.

A `type` step can contain a `{{secret:NAME}}` placeholder. The tool-server fills the value at run time and redacts the value in the report. See [Secrets](/docs/reference/configuration#secrets).

A step can read an earlier script's output with `{{output:…}}`. See [Script output](#script-output).

A gesture that resolves no selector passes with a warning when the runner cannot read the UI tree. This covers a coordinate `tap`, a `swipe` with no selector at either end, and a `pinch` or `rotate` without `on`. The warning says that Argent sent the gesture, not that the gesture reached the element.

### Launch map

Use the map form for a flow that runs on more than one platform:

```yaml
- launch: { native: com.acme.app, chromium: ../../app }
- launch: { ios: com.acme.app, android: com.acme.app.android, chromium: ../../app }
```

`native` is one id for iOS, Android and Vega. A per-platform key replaces it for that platform. `chromium` accepts a relative or absolute app path, or `{ path, args }`. A launch that has no id for the platform of the run is an error.

An Android app that starts from a non-launcher activity has no `launch:` form. Record `restart-app` with `activity` as a `tool` step and keep the flow as a fragment.

### Swipe

```yaml
- swipe: left
- swipe: { from: { id: story-card }, direction: left }
- swipe: { by: { y: -0.4 }, duration: 600 }
- swipe: { from: { id: drag-handle }, to: { id: drop-zone }, momentum: false }
```

A swipe moves one finger across the screen. `direction` is the travel of the finger, not the travel of the content. To bring an element on screen use `scroll-to` not `swipe`.

| Option      | Value                                                                                                                                      |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `from`      | The start point. A selector or `{ x, y }`. Argent selects the start when `from` is absent                                                  |
| `direction` | `up`, `down`, `left` or `right`. Argent moves the finger a preset distance. With `from`, Argent clamps the travel on screen                |
| `to`        | The end point. A selector or `{ x, y }`                                                                                                    |
| `by`        | A signed delta `{ x, y }` in screen fractions. Argent delivers the exact delta. With `from`, a delta that leaves the screen fails the step |
| `momentum`  | `false` removes the fling at the default `duration`. Default `true`                                                                        |
| `duration`  | The travel time in milliseconds. Default 300, minimum 150, maximum 10000                                                                   |

A step takes exactly one of `direction`, `to` and `by`. Each travel must cover at least 0.03 of the screen. Parsing rejects a shorter `by`. A shorter `to` fails the step during the run.

On Chromium, Argent runs a swipe as a mouse drag. On Vega, a swipe fails like the other touch directives.

## Conditions

```yaml
- await: { visible: { id: settings-screen } }
- await: { hidden: { id: loading-spinner }, timeout: 15000 }
- assert: { exists: { id: notifications-toggle } }
- assert: { text: { in: { id: preference-status }, equals: Enabled } }
- assert: { text: { in: { id: result-count }, matches: '^\d+ results$' } }
```

| Condition | Holds when                                                       |
| --------- | ---------------------------------------------------------------- |
| `exists`  | An element matches the selector                                  |
| `visible` | A visible element matches the selector                           |
| `hidden`  | No visible element matches the selector                          |
| `text`    | The text of the element in `in` satisfies exactly one comparator |

The `text` comparators:

| Comparator | Match                           |
| ---------- | ------------------------------- |
| `contains` | Case-insensitive substring      |
| `equals`   | Case-insensitive full match     |
| `matches`  | Case-sensitive JavaScript regex |

A negative condition passes before the element appears, for a typo, and on the wrong screen. First prove the screen and the same selector with `visible`. Then perform the action and check `hidden`.

### Prove a navigation

Each screen change needs two checks:

```yaml
- await: { visible: { id: profile-screen } }
- await: { idle: true }
```

The identity selector must exist only on the destination. `idle` waits until the screen has content and stops changing in the UI tree and in the pixels.

```yaml
- await: { idle: true, stableFor: 400, timeout: 9000 }
```

| Option      | Default | Description                         |
| ----------- | ------- | ----------------------------------- |
| `stableFor` | 250 ms  | How long the screen must stay still |
| `timeout`   | 7500 ms | The budget of the whole wait        |

`idle` never fails a run. A screen that does not settle passes with a warning. The warning names the reason: the screen kept moving, a small part kept moving, the wait ended mid-hold, the tree stayed empty, only the tree settled, or too few reads. Read the warning before you accept the step.

One outcome stops the steps: the runner cannot read the UI tree at all. Argent marks the step as errored and skips the later steps. The [teardown list](#teardown) still runs.

`idle` has no `assert` form and no `when` form.

## Optional steps

```yaml
- when: { visible: { text: Got it } }
  steps:
    - tap: { text: Got it }
```

The guard accepts one `exists`, `visible`, `hidden` or `text` condition, or `{ platform: ios | android | chromium | vega }`. A UI guard uses the assert grace and rejects `timeout`. There is no `else`. A skipped block reports as skipped. A failure inside an entered block is a real failure. Do not put a required check inside `when:`.

## Composition

```yaml
- run: ../shared/login.yaml
```

A `run:` path resolves against the directory of the flow file that contains the step. The `.yaml` suffix is optional.

| Platform     | Behavior                                                                                                                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| iOS, Android | A nested fragment or end-to-end flow runs inline. A nested launch restarts the app                                                                                                          |
| Chromium     | Each `launch` step boots one instance. A later launch boots a fresh instance and stops the previous one of that app. Argent runs `swipe` as a mouse drag. `pinch` and `rotate` are rejected |
| Vega         | Use `tool: tv-remote` and `tool: keyboard`. The touch directives are unsupported                                                                                                            |

A fragment whose `run:` chain reaches a launch cannot declare `executionPrerequisite`. Parsing accepts the file, the run rejects it.

A fragment can have its own teardown list. Argent runs that list when the steps of the fragment end. See [Teardown in a fragment](#teardown-in-a-fragment).

## Snapshots

```yaml
- snapshot: checkout-summary
- snapshot: { name: price-card, cropOn: { id: price-card }, maxMismatch: 0.2 }
```

A snapshot compares the current screen, or the frame of `cropOn`, with a stored baseline. A missing baseline fails the step. A mismatch above `maxMismatch` percent fails the step. The default `maxMismatch` is 0.5. A `cropOn` element whose size changed fails the step.

Baselines live in `.argent/flows/__baselines__/<flow>/`. Argent keys a baseline by platform and capture geometry, plus the selector for `cropOn`. Run `argent flow run <name> --update-baselines` to write the baselines from a known-good state. Review each baseline before you commit it.

Use a snapshot for layout, color, spacing, typography, clipping and icons. Do not use a snapshot as the only proof of navigation, data or network behavior. Avoid timestamps, live data, ads and animation in the captured region. The runner pins the mobile status bar during a visual run.

## Local scripts

```yaml
- script: { path: ../../scripts/seed-order.mjs }
- script: { path: ../../scripts/seed-order.sh }
- script: { path: ../../scripts/seed-order.mjs, timeout: 60000 }
```

Use a `script` step for setup or cleanup that device steps cannot do. The script is a local `.mjs` or `.sh` file.

Put a cleanup script in the [teardown list](#teardown). Then Argent also runs the cleanup after a failed step. The recording tools do not write the teardown list. Add it by hand after the recording.

An `.mjs` file runs under Node.js. A `.sh` file runs under Bash. See [Bash scripts](#bash-scripts).

A script can return data for later steps. See [Script output](#script-output).

A `script` step needs no device. A flow of script steps alone runs with no simulator, emulator or browser, and the report names no device. A `run` step or a `when` step beside it makes the flow resolve one again, so a script inside a `when: { platform: ios }` block needs a booted iOS device.

The value is always a map. Parsing rejects a bare path, such as `script: scripts/seed-order.sh`.

| Key       | Required | Description                                                                                                                      |
| --------- | -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `path`    | yes      | An `.mjs` or `.sh` file, relative to the flow file that holds the step. Use a lowercase extension. Match the letter case on disk |
| `timeout` | no       | The time limit of the step in milliseconds. The minimum is 100, and the default is 30000                                         |
| `env`     | no       | Environment values for this script. See [Environment values](#environment-values)                                                |

Argent runs the script with the project root as the working directory. Argent gives the script an allowlist of environment names. Argent copies each value from the tool-server, not from the shell that starts the run. The tool-server is a long-lived process, so the values are the ones it held when it started. A variable you export now reaches a script only after you restart the tool-server. See [Environment variables](/docs/reference/configuration#environment-variables). The allowlist holds these groups:

- `PATH`, `HOME` and the equivalent Windows names
- The identity, shell, locale, terminal, temporary-directory and cache names of the host
- The Windows platform names
- The proxy names and the TLS certificate names
- The Node, npm, Android, Java and Apple toolchain names
- `CI`, `SSH_AUTH_SOCK`, and each name that starts with `npm_config_`

Argent removes each other name. Argent removes its own token, its own port and each `ARGENT_SECRET_` value. Argent does not read a project `.env` file, so a name such as `NODE_ENV` or `DATABASE_URL` is absent by default. Supply additional [environment values](#environment-values) through `env` or `scripts.env.allow`.

Three entries in the list give access to a credential. Each entry holds the value of the tool-server. `SSH_AUTH_SOCK` reaches the SSH agent of the session that started the tool-server. An `npm_config_` name can hold a registry token. `HOME` is the home directory of that session, so the script reads `~/.npmrc`, `~/.aws/credentials` and `~/.argent/` from there. Run a script only when you trust it.

`PATH` is the value of the tool-server too. A script that runs `psql`, `docker` or `pnpm` finds the binary on that `PATH`. An editor that starts the tool-server gives it the `PATH` of the editor. An `.mjs` script runs under the Node binary of the tool-server, not the binary on the `PATH` of your shell. In a `.sh` script, a `node` command uses this `PATH`.

The script log contains stdout and stderr from the script and its commands. Argent keeps at most 64 KiB per step and 256 KiB per flow. The log appears in these places:

- `scriptLog` in the step report. `scriptLogTruncated` is `true` if the log is incomplete. `teardown` is `true` for a teardown step.
- `log` in the result of `flow-add-script`. `logTruncated` is `true` if the log is incomplete.
- The output of `argent flow run`, below the step.

If log collection stops before the commands finish, the step report includes a note.

Teardown scripts use the same 256 KiB budget as the other steps of the flow. Argent keeps no part of the budget for the teardown list. A large log from earlier steps can leave a teardown script with an empty log. `scriptLogTruncated` then shows `true`.

A failed step stops `steps`. The [teardown list](#teardown) still runs. The verdict names the side that caused the failure.

| Verdict | Cause      | Examples                                                                                                                   |
| ------- | ---------- | -------------------------------------------------------------------------------------------------------------------------- |
| Failed  | The script | A missing file, a load error, a thrown error, or a non-zero exit code                                                      |
| Errored | The host   | A time limit, a heap limit, a signal, a process that did not start, a full queue, a cancelled run, or a mis-cased filename |

A step that a thrown error stopped reports the message of the error and the frames of the script. Argent gives each frame a path relative to the project root. Argent removes the frames of Node and of its own runner, and keeps at most six.

The split holds only when the `timeout` is generous. Argent needs about a second to tell a script that never settles from a script the host stopped. Below that, the same defect of the script becomes a time limit, and the step is errored. Give a script a second or more before you read `errored` as a fact about the machine.

Parsing rejects a `timeout` below 100 milliseconds. The step starts a process before the script runs, and that start alone costs tens of milliseconds. A smaller limit ends the step at the time limit, or makes the result depend on the load of the host.

`timeout` bounds the run of the script, not the duration of the step. The tool-server runs a limited number of scripts at the same time, and it takes the number from the CPU count of the host. A step waits for a free slot before the script starts, and that wait can be longer than the `timeout` of the step. A step that finds the queue full is an errored step. Every project on the host shares one queue, because every project shares one tool-server.

Bash selection and log collection also occur outside `timeout`.

`scripts.maxTimeoutMs` caps the `timeout` of each step, and `scripts.heapLimitMb` sets the heap of the Node process. The heap limit does not apply to Bash. Argent reads both keys from the global configuration file of the tool-server's own home directory. See [Available keys](/docs/reference/configuration#available-keys).

On iOS, Android and Vega, a `script` step above the `launch` step runs before Argent restarts the app.

On Chromium, Argent boots the app before step 1 only when the run has no `device` and the leading `launch` names a Chromium app alone. A `script` step above that `launch` then runs while the app is up. In every other case Argent boots nothing before step 1: the `script` step runs first, and the `launch` step attaches to a running instance. Two cases reach it — a run you pin with `--device`, and a `launch` that names more than one platform when you pass no `--platform`.

### Bash scripts

Argent runs `.sh` files with Bash. The file needs no execute permission. Argent ignores the `#!` line and supplies no arguments or standard input.

#### Select Bash

Argent searches for Bash in this order:

1. The absolute path in the global `scripts.bash` key.
2. `bash` on the `PATH` of the tool-server.
3. `/bin/bash`, then `/usr/bin/bash`. On Windows, Argent searches the Git for Windows installation.

An invalid `scripts.bash` value stops the step with an error. Argent does not support the Windows WSL launcher.

To use a specific Bash version, set `scripts.bash` to its absolute path. See [Available keys](/docs/reference/configuration#available-keys).

#### Write a script

Start the script with `set -euo pipefail` to stop on command failures and undefined variables. Use LF line endings. To preserve LF in Git, add this rule to `.gitattributes`:

```gitattributes
*.sh text eol=lf
```

Stop each background job by its process ID before the script exits. Do not use `trap 'kill 0' EXIT`; it can stop Bash itself.

#### Check failures

A nonzero exit code fails the step. The failure reason includes the exit code and the last non-blank line from stderr. Argent includes stdout only in the log, not in the reason.

To report a failure, write the explanation to stderr. Then exit with a nonzero code:

```bash
echo "The orders API returned 503" >&2
exit 1
```

| Symptom                    | Action                                                                                                     |
| -------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Exit code `126`            | Check that Bash can read the script and execute its commands.                                              |
| Exit code `127`            | Check that the command is on the `PATH` of the tool-server. Restart the tool-server after a `PATH` change. |
| `$'\r': command not found` | Convert the script from CRLF to LF line endings.                                                           |

On Windows, Bash from Git for Windows gives its own commands priority on `PATH`.

## Environment values

Use top-level `env` for script defaults and `script.env` for one step. Read values with `process.env.NAME` in `.mjs` or `$NAME` in `.sh`:

```yaml
env:
  API_URL: https://api.example.com
steps:
  - script:
      path: ../../scripts/create-user.mjs
      env:
        API_KEY: "{{secret:API_KEY}}"
        USER_TYPE: premium
```

Override defaults with `argent flow run <name> --env NAME=value` or `flow-execute`'s `env` parameter. Precedence, highest first: script step, run values, nested flow defaults, parent defaults, allowed host variables.

A `run:` inherits values; its defaults apply only inside that flow. A raw `tool: flow-execute` starts a separate run: pass values in `args.env`.

Use string values; quote numbers and booleans. Names must match `[A-Za-z_][A-Za-z0-9_]*`; on Windows, avoid names that differ only in case. Argent rejects a reserved name.

[Output references](#output-references) work in `script.env`. They do not work in top-level `env`, `--env`, or the `flow-execute` parameter `env`.

A `tool: flow-execute` step can pass output values through `args.env`. The parent flow resolves these references before the child flow starts.

Add top-level `env` and `teardown` after recording. Save both before re-recording: `flow-start-recording` clears the whole file.

### Secrets in an `env` value

Use `{{secret:NAME}}` for credentials; configure them in the tool-server's [secret sources](/docs/reference/configuration#secrets). Missing secrets prevent the script from starting.

Argent redacts resolved secrets in script failures and logs, but not every encoding. Plaintext `env` values and returned output documents remain visible. Do not put credentials in logs or output documents.

### Inheriting host variables

[`scripts.env.allow`](/docs/reference/configuration#available-keys) adds names inherited from the tool-server. A later shell `export` does not update it. For a missing value or command, pass the value or `PATH` through `env`, or restart the tool-server with the required environment.

## Script output

A script can save data for later steps in an output document. Use `{{output:path}}` to read a value:

```yaml
steps:
  - script:
      path: ../../scripts/create-user.mjs
  - type:
      into: { id: user-name }
      text: "{{output:user.displayName}}"
  - echo: "Created user {{output:user.id}}"
```

### Output document

The output document is a JSON object. Each run starts with an empty document. Nested `run:` flows and `when` blocks share that document. A `tool: flow-execute` step starts a separate run with its own empty document.

In an `.mjs` script, read or change the `output` global:

```js
output.user = { id: "42", displayName: "Test user" };
```

You can also assign an object with `output = { user, orderId };`.

In a `.sh` script, `$ARGENT_OUTPUT` is the path to a file with the current document. Write a JSON object to that file:

```bash
printf '%s\n' '{"user":{"id":"42","displayName":"Test user"}}' > "$ARGENT_OUTPUT"
```

If a command reads `$ARGENT_OUTPUT`, write its result to a second file. Then move that file to `$ARGENT_OUTPUT`. Direct redirection empties the source file before the command reads it.

After a successful script step, Argent updates the output document:

- Each returned top-level key replaces its previous value, including nested values.
- Other top-level keys keep their values. To clear a key, set it to `null`.
- Argent ignores output from failed scripts.

Use JSON objects, arrays, strings, finite numbers, booleans and `null` as values. Keep each returned document and the combined document at or below 1 MiB. Use strings for identifiers, prices and codes to preserve their exact values.

Output values can appear in logs and failure reports. Use [secrets](#secrets-in-an-env-value) for credentials.

### Output references

A reference starts with `{{output:` and ends with `}}`. Put quotation marks around YAML values that contain references.

| Reference                              | Reads                                                |
| -------------------------------------- | ---------------------------------------------------- |
| `{{output:user.displayName}}`          | An object property                                   |
| `{{output:codes[0]}}`                  | The first array element                              |
| `{{output:order['order-id']}}`         | A property with a hyphen in its name                 |
| `{{output:user.promo.code ?? 'NONE'}}` | The code, or `NONE` if the path is missing or `null` |

Use `??` to supply a fallback path or a literal value. A literal can be a quoted string, number, boolean or `null`. Argent tries the alternatives from left to right:

```yaml
- echo: "Region {{output:user.region ?? defaults.region ?? 'unknown'}}"
```

If no alternative supplies a value, the step is errored and stops `steps`, as a failed step does. This also applies to `when` conditions. References support only paths and `??` fallbacks. Calculate other values in the script. For a teardown step, see [Missing output values](#missing-output-values).

### Reference fields

References work in these fields:

| Field                                             | Supported values                                             |
| ------------------------------------------------- | ------------------------------------------------------------ |
| `echo`                                            | Message text                                                 |
| Selectors, including scopes and `when` conditions | `text`, `id` and `role`                                      |
| `type`                                            | `text`                                                       |
| Text checks, including `when` conditions          | `contains` and `equals`                                      |
| `script.env`                                      | Environment values                                           |
| `tool.args`                                       | String values, including values in nested objects and arrays |

Keep paths, `launch` values, snapshot names, `executionPrerequisite`, tool names and `matches` patterns literal. For `tool: flow-execute`, this also applies to `flow_path`, `project_root`, `name` and `flow_file`. Tool names inside `tool: run-sequence` must also stay literal.

### Value types

In `tool.args`, a field that contains only one reference keeps the referenced value's JSON type. The value must match the tool parameter's type. For example, `keyboard` requires a string in `text`. A `type` step converts a referenced number to text.

Other fields convert strings, numbers and booleans to text. An `args` value with text around a reference also uses this conversion. Only `echo` accepts objects, arrays and `null` as text; it prints them as JSON.

Selectors, text checks and `type` need nonempty values. Do not use `?? ''` as their complete value. A selector's `text` must contain a visible character.

Write secret placeholders directly in the flow file. Do not build them from output values.

### Record script output

Recorded scripts share an output document. Record each script with `flow-add-script`. Use references in its `env` or in the `args` of a later `flow-add-step` call.

Argent resolves these references before the call and saves them for replay. If a reference has no value, the call does not run or record a step. `flow-add-echo` can record an unresolved reference, but its result includes a warning.

## Teardown

The top-level `teardown` key holds a list of steps. A step in this list is a teardown step. Argent runs the teardown list after `steps` ends, also after a failure. Use the teardown list to remove the backend data that the flow made, for example a test order or a test account.

```yaml
env:
  API_URL: https://api.example.com
steps:
  - script: { path: ../../scripts/seed-order.mjs }
  - launch: com.example.shop
  - tap: { text: Checkout }

teardown:
  - script: { path: ../../scripts/delete-order.sh }
```

`seed-order.mjs` writes the order id to the [output document](#output-document). `delete-order.sh` reads the id from `$ARGENT_OUTPUT`:

```bash
set -euo pipefail
order_id=$(jq -r '.order.id // empty' "$ARGENT_OUTPUT")
if [ -z "$order_id" ]; then
  echo "No order was created. Nothing to delete."
  exit 0
fi
curl -fsS -X DELETE "$API_URL/orders/$order_id"
```

`seed-order.mjs` can stop before it writes the id. For a missing key, `jq -r .order.id` prints `null`. Without `// empty` and the `-z` test, the script sends `DELETE /orders/null`.

### When the teardown list runs

| End of `steps`            | Teardown list          |
| ------------------------- | ---------------------- |
| No step failed or errored | Argent runs it         |
| A step failed or errored  | Argent runs it         |
| A cancel stopped the run  | Argent does not run it |

A cancel is one of these events:

- You press Ctrl+C during `argent flow run`.
- The connection between the Argent MCP server and the tool-server closes.
- The tool-server stops.
- The caller reaches its [time limit](#time-limit-of-the-caller).

A cancel request from the MCP client does not cancel the run. The run continues, and Argent runs its teardown list.

After a cancel, no teardown step starts. The caller gets no report of the teardown list. The backend data of the cancelled run stays. Write each setup script so that it operates correctly with the data of an earlier run.

A cancel during the teardown list stops the list. The remaining teardown steps do not start.

Argent runs a teardown list only for a flow that started its steps. Argent runs no teardown list in these cases:

- The run stops before its first step. The cause is device resolution, a Chromium boot, a parse error, a [missing teardown secret](#secrets-in-a-teardown-list), or the `executionPrerequisite` notice.
- Argent skips a `run:` step, finds a cycle at it, or cannot load its file. Argent runs the steps and the teardown list of a fragment only when its `run:` step starts.

A failed or errored teardown step makes a passed run fail. A teardown list that passes does not make a failed run pass:

| `steps`                   | Teardown list                      | `ok` of the run |
| ------------------------- | ---------------------------------- | --------------- |
| No step failed or errored | No teardown step failed or errored | `true`          |
| No step failed or errored | A teardown step failed or errored  | `false`         |
| A step failed or errored  | Any result                         | `false`         |

### Time limit of the caller

The `argent flow run` command and the Argent MCP server wait at most 5 minutes for data from the tool-server. If a run sends no data for 5 minutes, the caller closes the connection. Argent then cancels the run and does not run its teardown list. Thus the backend data stays.

| Caller                                                                     | The run sends data         | The limit applies to                                                |
| -------------------------------------------------------------------------- | -------------------------- | ------------------------------------------------------------------- |
| `argent flow run` for one flow without `--json`, also with `--json-stream` | After each step            | The time before the first step report, and between two step reports |
| `argent flow run --json`, a directory run, and the MCP `flow-execute` tool | At the end of the run only | The full run time of each flow                                      |

These steps can take 5 minutes before or between step reports:

- A slow script, or a script that waits for a free slot.
- A `script` step with a `timeout` near 5 minutes. The default [`scripts.maxTimeoutMs`](/docs/reference/configuration#available-keys) is 5 minutes.
- A `tool: flow-execute` step. The child run sends no step reports to the parent run.

After the cancel, the Argent MCP server sends the same run again, up to 4 more times. Each new run starts at step 1 and runs the setup scripts again. Keep a flow with a teardown list below the 5-minute limit.

### Failures in a teardown list

A teardown list stops at its first teardown step that fails or is errored. Argent does not continue, because a device step operates on the screen that the previous step left. Argent reports each later teardown step of that list as skipped, with a reason:

```text
did not start: the teardown list stopped at tap "Settings"
```

A skipped teardown step can leave backend data. Thus the first skipped teardown step that is not an `echo` step also gets a warning. The warning names the skipped teardown steps of the list that are not `echo` steps. The warning names at most 10 steps and then gives the number of the other steps:

```text
this and 1 more teardown step did not start because the teardown list stopped at tap "Settings": tool stop-all-simulator-servers, script scripts/delete-user.sh. What they clean up can remain
```

Argent gives no warning when the step that stopped the list is the last step of that list. Argent also gives no warning when only `echo` steps remain. The summary of `argent flow run` counts the warning.

Put the backend cleanup scripts before the device steps in a teardown list. Then an app crash cannot stop the cleanup.

Argent checks the path of a teardown script only when the step starts. An incorrect path shows as a failed teardown step at the end of the run. Read the report of the first run that uses a new teardown list.

### Teardown in a fragment

A fragment can have its own teardown list. Argent runs that list when the steps of the fragment end, before the next parent step. Thus teardown lists run from the inner flow to the outer flow.

The teardown list of a fragment cannot keep data for its parent. For example, a `create-account.yaml` fragment makes an account for the parent. If the fragment deletes the account in its teardown list, the next parent step has no account. Put the cleanup in the teardown list of the flow that uses the data.

A teardown step of a fragment uses the scope of the fragment. It resolves paths against the directory of the fragment. It reads the `env` defaults of the fragment.

If a teardown step of a fragment fails or is errored, Argent skips the remaining parent steps. Argent then runs the teardown list of the parent.

A `run:` step in a teardown list is a teardown step. A failure in its fragment stops that teardown list.

A fragment with only a teardown list must also declare `steps: []`.

### Steps in a teardown list

A teardown list accepts the same steps as `steps`, except `snapshot`:

- Parsing rejects a `snapshot` step in a teardown list, also inside a `when` block. With `--update-baselines`, such a step can store the screen of a failed run as the baseline.
- A `snapshot` step in a fragment that a teardown `run:` step starts is errored.

Parsing accepts `teardown: []`. Parsing rejects `teardown:` with no value, and any value that is not a list. An output reference error or a `snapshot` error names the teardown step `Teardown step N`. For example, `Teardown step 2.1` is the first step in the `when` block of teardown step 2. Other parse errors of a teardown step do not name its position.

Argent reads only `steps` to find the [shape](#file-shape) of a flow. A `launch:` step in a teardown list does not make a flow end-to-end. Argent does not boot the app of a teardown `launch:` step before step 1. Thus a flow with a Chromium `launch:` step only in its teardown list runs on the device that Argent finds. For such a flow, pass `--device` with a Chromium instance.

On Chromium, these rules apply:

- A teardown `launch:` step always operates as a later launch. It boots a new instance and stops the earlier instance of that app that the run booted.
- After the teardown list of a fragment, Argent moves the run back to the instance that the run used before that list. If the run booted that instance and the list launched that app again, Argent moves the run to the new instance of the app. If that launch failed, the run stays on the instance that the list used last. When Argent moves the run, Argent also brings the page of that instance to the front.

### Output in a teardown list

Teardown steps read and write the [output document](#output-document) of the run, with the same merge rule as `steps`. A teardown script receives the values that the run saved before it stopped. A `.sh` script reads them from `$ARGENT_OUTPUT`. An `.mjs` script reads the `output` global.

A teardown step cannot remove data that it cannot find. Make each script that makes backend data write the id to the output document. Argent ignores the output of a failed script. Thus a script that fails after it makes backend data must remove that data itself.

A `tool: flow-execute` step starts a separate run with its own output document and its own teardown list. That teardown list cannot read the output of the parent flow. Pass the ids to the child flow through `args.env`.

#### Missing output values

A missing `{{output:…}}` value in a teardown step is an error, as it is in `steps`. The error stops the teardown list. Usually no step wrote the value, because the setup script failed or its `when` block did not run.

Use one of these forms for a value that can be missing:

| Location of the value                                | Form                                                                                                                                 |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| A `.sh` script that reads `$ARGENT_OUTPUT`           | Read the value with `jq -r '.order.id // empty'`. Exit with code 0 when the value is empty. See the example in [Teardown](#teardown) |
| A script `env` value, a `tool` argument or an `echo` | Add a `??` fallback, for example `?? ''`. Make sure that the step operates with an empty value                                       |
| A selector, a text check or `type` text              | Put the step in a `when` block. Give the guard reference a fallback that no screen shows, for example `?? '__none__'`                |
| A `when` guard                                       | Give the reference a fallback that no screen shows, for example `?? '__none__'`                                                      |

```yaml
teardown:
  - script:
      path: ../../scripts/delete-order.sh
      env: { ORDER_ID: "{{output:order.id ?? ''}}" }
  - when: { visible: { text: "{{output:order.id ?? '__none__'}}" } }
    steps:
      - tap: { text: "{{output:order.id}}" }
```

A fallback cannot make a selector, a text check or `type` text optional, because these fields reject an empty value. When the value is missing, the `'__none__'` fallback makes the guard false. Argent then skips the block, and the teardown list continues. The references inside the block need no fallback, because Argent enters the block only when the value exists.

This guard form works for an `exists`, `visible` or `text` guard. It does not work for a `hidden` guard, because a missing element makes that guard true.

When an earlier step of the run did not pass, Argent adds a hint to the error reason. The hint names the first step of the run that did not pass: a failed, errored or skipped step. The hint then recommends the form for the location of the value. Argent gives no hint when all earlier steps passed. In that case, the reference or the script is incorrect.

### Secrets in a teardown list

Argent resolves the `{{secret:NAME}}` placeholders of the teardown list before the run starts. Argent then discards the values. A missing secret stops the run before Argent selects a device, boots an app or starts a step. Thus a run on a computer without a CI secret stops before it makes backend data.

Argent checks these fields:

| Field                                                                                  | `<project-root>` of the secret sources   |
| -------------------------------------------------------------------------------------- | ---------------------------------------- |
| The `env` values that a teardown `script` step receives                                | The `project_root` of the run            |
| `type` text                                                                            | The working directory of the tool-server |
| `args.text` of `tool: keyboard` and `tool: paste`                                      | The working directory of the tool-server |
| `args.steps[].args.text` of the `keyboard` and `paste` entries in `tool: run-sequence` | The working directory of the tool-server |
| `args.env` of `tool: flow-execute`                                                     | The `project_root` of that call          |

The `env` values of a script step include the top-level `env`, the run values and the step `env`. A step value or a run value that replaces a top-level placeholder removes that placeholder from the check. For the secret sources, see [Secrets](/docs/reference/configuration#secrets).

Argent also reads the file of each `run:` step in the teardown list. Argent checks the steps and the teardown list of that file. For a fragment that a step in `steps` starts, Argent checks only the teardown list of the fragment, when its `run:` step loads the file. A missing secret there, outside a `when` block, makes the `run:` step errored, and no fragment step starts. Argent checks the steps of that fragment when each step starts.

Argent does not check these placeholders before the run:

- Placeholders inside a `when` block, also in the teardown list of a fragment. Argent does not know the platform before the run, and a guard can skip the block. Argent checks such a placeholder when its step starts.
- Placeholders in the flow file of a teardown `tool: flow-execute` step.
- Placeholders in `steps`. Argent checks each of them when its step starts.

### Teardown in the report

Each report of a teardown list holds `teardown: true`. This includes these reports:

- The teardown steps.
- The `run:` and `when` markers in a teardown list, and the steps of their fragments and blocks.
- The skipped teardown steps.
- The teardown list of a fragment inside the parent `steps`.

The `depth` field does not change. The report of each skipped `tool:` step, also in `steps`, holds its `tool` field.

`argent flow run` prints a label line, such as `──── teardown`, before each teardown section. The word `teardown` has the indentation of the section depth. The MCP result shows a `── teardown ──` block at the same position.

When the child run of a `tool: flow-execute` step fails, the reason of that step names the first failed step of the child run. If a teardown step of the child run failed after it, the reason also names that teardown step.

### Record a teardown list

The recording tools do not write the `teardown` key. Add the teardown list by hand after the `flow-finish-recording` call. `flow-start-recording` clears the whole file. Save the teardown list before a new recording, and add it again after the recording.

On a co-located tool-server, `flow-add-step`, `flow-add-script` and `flow-add-echo` keep a `teardown` list that the file already holds. On a tool-server on a different machine, each recording call replaces the whole file. There, add `teardown` only after the `flow-finish-recording` call.

A teardown script has no recorded form. To run a cleanup script live, record it with `flow-add-script`. After `flow-finish-recording`, move the step from `steps` to `teardown` by hand.

## The `argent flow` command

`argent flow run` replays a flow without an agent and exits non-zero on failure. The command always uses a local tool-server.

| Command                       | Description                                          |
| ----------------------------- | ---------------------------------------------------- |
| `argent flow run <name>`      | Run `.argent/flows/<name>.yaml`                      |
| `argent flow run <path>.yaml` | Run any flow file. The path must not contain `..`    |
| `argent flow run <dir>`       | Run every flow in the directory, one after the other |
| `argent flow list`            | List the flow files in `.argent/flows`               |

| Option               | Description                                                                                                                                                       |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--device <id>`      | The device to run on. Argent detects the device when you omit the option. A physical iPhone is never detected; name it here                                       |
| `--platform <p>`     | `ios`, `android`, `chromium`, `vega` or `ios-remote`. Narrows the detection. `ios` still never picks a physical iPhone, and never picks a remote simulator either |
| `--update-baselines` | Write the snapshot baselines instead of comparing them                                                                                                            |
| `--output <dir>`     | Write the failed baseline, current and diff images to `<dir>/<flow>/`, for a CI artifact upload                                                                   |
| `-r, --recursive`    | With a directory, also run the flows in subdirectories. Dot-directories and `node_modules` are skipped                                                            |
| `--env <NAME=value>` | Set a script environment value for this run. Repeat for each variable. See [Environment values](#environment-values)                                              |
| `--json`             | Print the JSON report of the flow, or the JSON aggregate of the directory                                                                                         |
| `--json-stream`      | Print one JSON record per line: each step, then the result. One flow, and not with `--json`                                                                       |
| `--`                 | End of options, for a flow name that starts with `-`                                                                                                              |

```bash
argent flow run checkout --platform ios
argent flow run .argent/flows/checkout.yaml --output flow-artifacts --json
argent flow run ~/shared-flows/checkout.yaml --device <UDID> --update-baselines
argent flow run .argent/flows --recursive
argent flow run checkout --env BUILD=1421 --env BASE_URL=https://staging.example.com
```

`--env` uses everything after the first `=` as the value. Quote values with spaces, for example `--env "LABEL=Test account"`. If you repeat a name, Argent uses its last value.

The file name without `.yaml` names the report and the artifacts. It contains only letters, numbers, `_` and `-`.

A directory run prints a numbered header for each flow. Under the header Argent prints each step of that flow that failed or carries a warning, with its artifact paths. Argent then prints one outcome line. Argent prints a summary of all flows at the end.

A flow that fails its steps lets the directory run continue. So does a flow that the tool-server rejects up front, such as an invalid file or a device that Argent cannot resolve. A transport failure ends the directory run. So does a rejection that the tool-server does not mark as a validation error, and a reply that is not a report. Invalid run arguments, such as a bad `--env` name, also stop the directory run. Argent counts the flows after the failure as skipped.

The outcome line of a flow that produced a report gives the result and the step counts of that flow. The outcome line of a flow that produced no report states the reason. A single flow run prints the same reason under the name of the flow.

| Outcome line                     | Meaning                                                         |
| -------------------------------- | --------------------------------------------------------------- |
| `not run (invalid flow)`         | The tool-server rejected the flow file or one of its steps      |
| `not run (no device resolved)`   | Argent did not resolve one device for the flow                  |
| `not run (rejected)`             | The tool-server rejected the flow for another reason            |
| `did not finish (run error)`     | The run failed before it produced a report                      |
| `did not finish (no run report)` | The tool-server answered without a run report                   |
| `not run (batch stopped)`        | An earlier failure ended the directory run. Directory runs only |

`--json` and `--json-stream` print no header, no outcome line and no summary.

A directory run with `--json` writes one document. The document holds `ok`, `total`, `passed`, `failed`, `skipped` and a `flows` array. The array holds one entry for each flow. Each entry holds the `path` and the `status`. An entry holds `report` when the flow produced one, whether it passed or failed its steps. An entry holds `error` instead when the tool call produced no report — a rejected run, a run error, or a reply that is not a report. Such an entry also holds `error_code` and `error_kind` when the tool-server sends them. An entry with the status `skip` holds neither, because Argent made no call for that flow. `--json-stream` puts the same two fields on its `error` record.

A single flow run with `--json` writes the report of that flow. When the run gets no report, Argent puts the reason on stderr instead. Use `--json-stream` to get the failure as a record.

In `--json` and `--json-stream` output, each step report of a teardown list holds `teardown: true`. A CI job can use this field to tell a teardown failure from a step failure. See [Teardown in the report](#teardown-in-the-report).

Pin `--platform` and `--device` on iOS, Android and Vega. On Chromium, pass `--platform chromium` and omit `--device`. Then the runner boots the declared app path with a reproducible window size.

## Remote runs

The `flow-execute` tool takes one flow source: `name` for a saved flow, or `flow_path` for any file. `run:` targets and baselines resolve on the file system of the tool-server. When the tool-server runs on a different machine, a `name` run sends only that one file. Argent checks the whole flow before it runs any step. Argent rejects a `run:`, `script:` or `snapshot` step at any depth, also in the teardown list. The error names the missing co-location, not a missing fragment, script or baseline. The tool-server refuses `flow_path` when the agent and the tool-server do not share a file system.

## YAML safety

Quote a string that contains `#`, `:` or quotes. Quote a value that holds an `{{output:…}}` reference. Quote a number, `true` or `false` in a text slot. Use single quotes for a regex with backslashes. Parsing rejects an unknown directive, an invalid selector, an invalid regex, `else`, an unsupported option, and an end-to-end flow that declares `executionPrerequisite`. Parsing also rejects an unknown top-level key, a `teardown` value that is not a list, and a `snapshot` step in a teardown list.
